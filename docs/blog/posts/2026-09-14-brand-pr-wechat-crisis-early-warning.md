# 品牌公关团队如何搭建公众号危机预警机制：从滞后感知到分级响应

品牌陷入舆论风波时，第一篇报道很少来自竞品或大家日常盯着的头部媒体号，反而更可能出现在地方民生号、垂直行业媒体、消费者维权类自媒体，甚至是某个区域代理商或加盟商的个人公众号上。这类账号数量多、更新不规律，公关团队平时也不会把它们列入重点监测名单，结果往往是：事件已经发酵了半天，团队才从内部群聊转发里第一次看到那篇文章。

这种滞后带来的代价是具体的。危机公关最看重的"黄金响应窗口"通常以小时计，一旦错过，团队仓促发声容易前后口径不一致，外界也更容易把迟到的回应解读为回避或不重视。更麻烦的是，很多品牌根本不清楚一次舆情事件里到底哪些号是首发、哪些是跟发、传播路径是怎么扩散的——事后复盘只能靠人工翻聊天记录、截图拼时间线，效率低还容易漏掉关键节点。

这些问题的共同根源是：可能引爆舆情的信源太分散，人工盯守只能覆盖其中很小一部分，而且没有留下可回溯的结构化记录。要解决它，需要先把"可能第一时间提到品牌"的公众号变成可以持续采集、可以关键词匹配、可以按时间线复盘的数据，而不是继续依赖人眼刷屏。

## 把预警信源变成结构化数据流

[Mp2RSS](https://mp2rss.bugcode.dev) 的做法是：找到目标公众号任意一篇文章的链接（形如 `https://mp.weixin.qq.com/s?...`），贴入控制台即可订阅该文章所属的整个账号，此后该号发布的每篇新文章都会被持续收录，正文以 **Markdown** 结构化形式交付，从发文到数据可见平均 **2–3 小时**。登录只需要 GitHub / Google 账号，不涉及微信账号，方便公关团队用部门公用账号统一维护预警信源清单，不受个人手机登录状态限制。

对危机预警场景来说，这意味着可以把"发现"这件事从人力密集型工作变成一条数据管道：公关团队负责判断"哪些号有可能第一时间提到我们"，剩下的持续抓取、正文清洗、关键词匹配交给系统完成，人只在真正命中预警时介入判断和响应。

## 落地步骤

### 第一步：建立预警信源清单，而不是只盯竞品

危机预警和日常舆情监测的信源范围不一样。除了竞品和头部行业媒体，还应该纳入：品牌所在城市或区域的地方民生号、垂直行业的中小型媒体号、消费者维权与打假类自媒体、经销商或加盟商个人号（容易第一时间暴露内部矛盾）、监管部门通报的转载号。把这些账号任意一篇文章的链接贴入 Mp2RSS 完成订阅即可，操作方式参考[快速开始](/guide/quick-start)和[订阅管理指引](/guide/subscription)。

需要注意的是，首次订阅不会回溯历史文章，只从订阅时刻起收录该号后续发布的新文章。这意味着预警信源清单必须提前建好，等事件已经发生再临时订阅相关账号，是无法找回之前已发布内容的。

### 第二步：用 Open API 批量订阅并做关键词匹配

预警信源往往有几十上百个，逐个手动订阅效率太低，可以用 [Open API](/api/) 脚本化完成，鉴权方式为 Bearer Token（控制台的 Feed 密钥）：

```bash
curl -X POST "https://mp2rss.bugcode.dev/open-api/subscriptions" \
  -H "Authorization: Bearer $FEED_KEY" \
  -H "Content-Type: application/json" \
  -d '{"articleUrl": "https://mp.weixin.qq.com/s/xxxxxxxxx"}'
```

订阅完成后，定时拉取各号的最新文章，正文以 `contentMarkdown` 字段返回：

```bash
curl "https://mp2rss.bugcode.dev/open-api/subscriptions/{mpId}/articles?page=1&pageSize=100" \
  -H "Authorization: Bearer $FEED_KEY"
```

拿到的正文是干净的 Markdown，不含公众号页面的排版和图片占位符，可以直接跑关键词匹配脚本：品牌名、产品名、高管姓名、门店地址等命中即触发预警，不需要先做一轮网页解析。习惯命令行的团队，也可以用 `mp2rss` 工具本地定时拉取指定账号的最新文章，用法见 [CLI 文档](/cli/)，省去自己写抓取脚本的成本。

### 第三步：按命中程度设计分级响应

不是每条命中关键词的文章都需要立刻升级到管理层。可以按信源类型和命中关键词的敏感度分级：一级（涉及安全、维权、监管通报关键词，来自任意信源）直接推送给公关负责人和值班群；二级（提及品牌名但语气中性，来自地方号或行业媒体）汇总进日报，由值班同学人工复核；三级（竞品对比或行业综述中顺带提及）仅存档，不主动推送。把这套规则写进关键词匹配脚本的后处理逻辑，能避免"什么都推"导致的告警疲劳，也避免"漏推"真正需要快速响应的信号。

### 第四步：沉淀事件时间线，供事后复盘

把命中预警的文章按发布时间排序归档，就形成了一份该事件的传播时间线：哪个号首发、间隔多久有账号跟发、跟发账号的转述角度有没有偏差。这份记录不需要事后再去翻聊天记录拼凑，复盘会上直接调出时间线即可，也能为下一次修订预警信源清单提供依据——比如发现某个此前没有列入清单的地方号成了首发源，就把它补充进长期监测名单。

## 人工盯守与结构化预警管道对比

| 维度 | 人工盯守 | 结构化预警管道 |
| ---- | ---- | ---- |
| 信源覆盖 | 精力有限，通常只覆盖头部账号 | 可批量订阅地方号、垂直媒体、经销商号等长尾信源 |
| 发现时延 | 依赖内部转发，常滞后数小时到数天 | 平均 2–3 小时 |
| 响应分级 | 全靠人工判断轻重缓急 | 按信源类型与关键词命中程度预设规则 |
| 事后复盘 | 需要重新翻找截图与聊天记录 | 按事件时间线直接调取 |

## 常见问题

**这套机制能自动发现之前没订阅过的公众号吗？**
不能。预警覆盖范围取决于提前建好的信源清单，系统只持续采集已订阅账号的后续文章，不会主动抓取全网未订阅的公众号。因此信源清单的完整性需要公关团队定期复盘和补充。

**订阅之后能查到该号之前发过的历史文章吗？**
不能。首次订阅不回溯历史文章，只从订阅时刻起收录该号后续发布的新文章，这也是预警信源清单要尽早建好的原因。

**从对方发文到我方能查到，大概要等多久？**
平均 2–3 小时。这个时延足以支撑多数危机响应场景下的信息研判和口径准备，但不构成"秒级"或实时保证，如果需要更极端的实时性，仍建议保留人工紧急上报渠道作为补充。

**需要绑定微信账号才能使用吗？**
不需要。登录使用 GitHub 或 Google 账号，订阅动作只需要一篇目标公众号的文章链接，全程不涉及微信账号，适合用公关部门的公用账号集中管理。

**一个账号能同时监测多少个预警信源？**
按套餐档位区分：49 元/月 50 个订阅、99 元/月 100 个、399 元/月 400 个，三档功能一致，仅订阅上限不同，具体见[会员与计费](/guide/membership)。危机预警信源通常数量较多，可按需要覆盖的长尾账号规模选择合适档位。
