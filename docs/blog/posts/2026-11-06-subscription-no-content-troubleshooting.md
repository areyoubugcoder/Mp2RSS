# 订阅成功却没有文章？公众号与 X 内容逐步排查指南

“没有文章”可能指订阅列表为空，也可能是阅读器没刷新，或程序拿到了条目却没拿到正文。先确定缺失的是哪一步，再处理对应问题。订阅成功只说明订阅操作完成，不保证马上出现新内容或完整历史文章。

本指南用于已经尝试订阅的用户。还没建立订阅时，先按[快速开始](/guide/quick-start)完成操作。下面的步骤适用于公众号与 X，但两类信息源的管理入口和内容字段不同。

## 先记录一个具体样本

选择一个有问题的信息源，记下名称、原文链接、来源发布时间、订阅时间和你观察问题的时间。统一注明时区，避免把不同时区的显示误判为延迟。

然后回答三个问题：控制台能否找到该订阅？控制台是否已有目标内容？阅读器或程序实际返回了什么？如果目标只是订阅前发布的旧内容，先调整预期：服务不保证完整历史回溯，不应以某篇旧文章必然出现作为验收条件。

| 观察到的现象 | 优先检查 |
| --- | --- |
| 控制台找不到目标订阅 | 账户、订阅是否完成、源是否选对 |
| 能找到订阅，但控制台没有目标内容 | 来源发布时间、采集进度、内容类型 |
| 控制台有内容，阅读器没有 | Feed 地址、订阅范围、阅读器刷新与筛选 |
| 程序返回错误 | 凭据、会员、源 ID、订阅关系及限流信息 |
| 程序返回条目，但正文为空 | 内容字段、推文与长文的区别、正文是否可用 |

## 第一步：核对账户和会员状态

打开 [Mp2RSS 控制台](https://mp2rss.bugcode.dev)，确认当前账户就是建立订阅、开通会员时使用的账户。检查会员有效期和实际开通状态，付款记录不等于权益已经生效。试用资格及开通规则见[会员与计费](/guide/membership)。

阅读器中出现“会员已到期”等提示时，应先处理账户状态。这类提示属于服务通知，不能作为信息源内容正常更新的证据。也不要通过反复注册账户来排查阅读器或本地工具的问题。

## 第二步：确认订阅和内容类型

在订阅管理里查找目标来源，核对名称与身份。公众号用文章链接建立订阅时，应确认链接确实来自目标公众号；X 则在 Web 控制台搜索并订阅。

程序读取时，公众号使用 `mpId`，X 使用 `xUserId`，后者不是 `@用户名`。应从自己的订阅列表取得 ID，不要直接复制教程中的示例数字。

X 推文与长文分别查询。某个账号有推文，并不表示它发布过长文；长文列表为空时，应先确认查的是不是正确的内容类型。入口选择可参考[RSS、Open API、CLI 决策指南](/blog/posts/2026-11-06-rss-open-api-cli-how-to-choose)。

## 第三步：区分采集与阅读器刷新

先查看来源是否确有新发布内容，再比较控制台与阅读器。

- **控制台尚未出现目标内容**：记录原文链接与发布时间，稍后再次观察。来源发布、服务采集与阅读器刷新是不同环节，不承诺发文即达或每篇完整覆盖。
- **控制台已经有目标内容**：确认阅读器使用的是当前账户、正确范围的 Feed 地址，手动刷新一次，并检查是否开启了“仅未读”等筛选。
- **最近重置过 Feed 密钥**：从账户设置重新复制地址，替换阅读器中的旧地址。旧凭据不会因等待或重启阅读器恢复有效。

不要把反复取消订阅、重新订阅或高频刷新当作通用修复动作。它们不能证明采集已经完成，还会使订阅时间和问题现场更难判断。

## 第四步：程序错误与空结果分开处理

Open API 的状态码用于辅助定位。下表针对 Open API；Feed 链接的失败表现不能直接套用这套判断。

| 程序结果 | 建议动作 |
| --- | --- |
| 401 | 核对当前使用的凭据，重置过密钥后更新程序或重新授权 CLI |
| 403 | 核对账户会员状态，并结合实际错误信息确认原因 |
| 404 | 检查路径、源 ID 和当前账户是否订阅了该源 |
| 429 | 按 `Retry-After` 等待后重试，停止紧密循环请求 |
| 请求成功但 `items` 为空 | 检查源、分页与内容类型，再判断当前是否有可用内容 |

具体协议见[API 文档](/api/)。对于 CLI，可先核对版本、当前授权状态和订阅列表：

```bash
mp2rss --version
mp2rss auth status
mp2rss mp list -o json
mp2rss x list -o json
```

如果确需重新授权，按[登录指南](/cli/login)操作。检查环境变量是否覆盖了本地配置，但不要把密钥值打印到反馈或截图里。本地显示“已登录”并不能替代一次真实读取验证。

## 第五步：拿到条目后再确认正文

公众号文章和 X 长文的 `contentMarkdown` 可能为空；X 推文则检查 `content`。不能因为接口返回了标题、链接或条目数量，就认为全文已经可用。

如果任务需要总结全文，而返回正文为空，应标记“正文缺失”，保留原文链接，暂缓依赖全文的处理。不要让 Agent 根据标题补写不存在的内容。具体核对字段见[首次内容获取指南](/cli/first-delivery)。

## 常见排查问题

### 空列表是否说明账户被封禁？

不能据此判断。空列表、鉴权错误和会员状态是不同证据，应按上面的步骤分别检查。

### Feed 链接打不开，是否一定是密钥错了？

不一定。Feed 的失败响应不能单独证明原因；先从账户设置复制当前链接，并核对账户状态和地址是否完整。

### 重新安装 CLI 能解决正文为空吗？

不能据此保证。若请求已成功且返回正文为空，应检查内容可用性；只有命令缺失、版本或本地运行问题才需要处理安装环境。

### 仍无法定位，反馈时提供什么？

按[常见问题中的反馈入口](/guide/faq#反馈与支持)提交源名称、可公开的原文链接、带时区的时间、使用入口、错误信息及已做的检查。删除截图和日志中的 Feed 密钥、完整 Feed 地址与个人信息，不要公开私人内容。
