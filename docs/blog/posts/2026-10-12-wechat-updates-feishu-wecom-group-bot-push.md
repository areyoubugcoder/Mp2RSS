# 运营团队如何把公众号更新推送到企业微信/飞书群：群机器人提醒搭建法

很多团队的信息监测工作是这样分配的:某个同事负责盯几个行业公众号,看到有价值的更新就手动截图发到工作群里。这个流程能跑起来,但有一个明显的单点依赖——一旦这个人请假、换岗,或者当天漏看了订阅号消息列表,更新就直接漏给了整个团队,没有人会注意到「本来该有一条消息,但没有出现」。

更常见的情况是,团队里不止一个人关注同一批公众号,但彼此并不知道别人也在刷,于是经常出现「同一篇文章被两个人分别转发到群里」,或者反过来「大家都觉得别人会看,结果谁都没仔细看」。公众号更新停留在每个人自己的微信客户端里,没有变成团队共享的信息,群聊这个本该承载团队共同记忆的地方,反而成了信息的盲区。

还有一类团队已经把日常协作迁到了企业微信或飞书,工作沟通、审批、文档都在里面完成,公众号相关的信息却是唯一还要跳出去、打开另一个 App 才能看到的部分。对这些团队来说,真正需要的不是「指派一个人去刷公众号」,而是让关注的公众号更新像其他系统通知一样,自动出现在团队日常协作的那个群里。

## 靠人工值守监测公众号的团队会遇到的具体问题

- **单点依赖**:监测职责落在某一个人身上,这个人缺席或疏漏,整个团队就漏掉信息,没有备份机制。
- **信息不同步**:多人关注同一批号,但各自为战,容易重复劳动或互相依赖导致都没看。
- **协作场景割裂**:日常工作在企业微信 / 飞书里完成,公众号更新却要单独打开微信查看,两个工具之间没有打通。
- **新人接手成本高**:监测的号、关注的重点往往只存在负责人的脑子里,交接时很难完整说清楚「平时都在看什么」。
- **无法追溯**:群里偶尔转发的截图不成体系,想回头找「上周某个号到底发了什么」基本靠回忆和翻聊天记录。

这些问题的根源是公众号更新停留在个人微信账号层面,没有被转换成团队可以统一消费的结构化数据,自然也没办法接入企业微信或飞书的群机器人。

## 解决思路:把公众号转换成结构化数据,再用群机器人推送

[Mp2RSS](https://mp2rss.bugcode.dev) 负责的是第一步转换:把想监测的公众号的任意一篇文章链接(`https://mp.weixin.qq.com/s?...`)贴进去完成订阅,此后这个号发布的新文章会被持续收录,平均从发文到数据可见只需 2–3 小时。登录不需要绑定微信账号,用 GitHub 或 Google 账号即可完成,适合团队用统一账号集中管理监测列表。

有了结构化数据,第二步就是企业微信和飞书本身都提供的能力——群自定义机器人:群主或管理员在群设置里创建一个机器人,拿到一个 Webhook 地址,之后任何程序只要往这个地址发一条符合格式的 POST 请求,消息就会以机器人身份出现在群里。把这两步串起来,就是「公众号更新 → Mp2RSS 结构化数据 → 定时脚本检查增量 → 企业微信/飞书群机器人推送」的完整链路,不需要公众号方或微信本身提供任何推送能力。

## 落地步骤

### 第一步:把要监测的公众号批量订阅进同一个账户

用团队统一的账号登录 Mp2RSS,把需要监测的公众号逐个订阅,具体操作参考[订阅管理指引](/guide/subscription)。需要注意,首次订阅不会回溯历史文章,只从订阅时刻起收录新内容,所以确定要长期监测的号,建议立刻订阅,不要等到需要查历史时才想起来。

订阅数量上限由套餐档位决定,49 元/月 50 个订阅、99 元/月 100 个、399 元/月 400 个,功能完全一致仅上限不同,团队按监测号的数量选择合适档位,详见[会员与计费](/guide/membership)。

### 第二步:在企业微信或飞书群里创建自定义机器人

这一步在协作工具自己的群设置里完成,和 Mp2RSS 无关:

- **企业微信**:群聊右上角「...」→「添加群机器人」→ 创建后复制得到的 Webhook 地址;
- **飞书**:群设置 →「群机器人」→「添加机器人」→ 选择「自定义机器人」,同样复制 Webhook 地址。

拿到的 Webhook 地址要像密码一样保存,不要直接贴进公开仓库或聊天记录。

### 第三步:用 Open API 定时拉取新增文章

调用 [Open API](/api/) 查询某个公众号最新的文章列表:

```bash
curl "https://mp2rss.bugcode.dev/open-api/subscriptions/{mpId}/articles?page=1&pageSize=20" \
  -H "Authorization: Bearer {feed_key}"
```

返回结果按发布时间倒序排列,带标题、原文链接和发布时间(`publishedAt`,UTC 毫秒)。定时脚本(用 cron 每隔 15–30 分钟跑一次即可,不需要追求秒级)只需要记录「上次检查到的最新发布时间」,每次拿到结果后筛出比这个时间更新的文章,就是这一轮需要推送的增量,不需要每次全量比对。

如果监测的号比较多,先调用 `GET /open-api/subscriptions` 拿到完整的订阅列表和每个号的 `mpId`,再在脚本里循环遍历,逐个查询增量,避免漏掉任何一个号。

### 第四步:把增量文章拼成消息,推给群机器人

企业微信和飞书的自定义机器人都支持直接发送文本或图文卡片,一条最简单的文本消息请求大致是:

```bash
curl -X POST "https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key={企业微信机器人key}" \
  -H "Content-Type: application/json" \
  -d '{
    "msgtype": "text",
    "text": { "content": "【公众号更新】某行业观察 发布新文章:新能源补贴政策解读\nhttps://mp.weixin.qq.com/s/xxxxxxxxx" }
  }'
```

飞书的请求格式类似,换成飞书机器人自己的 Webhook 地址和消息体结构即可。把第三步筛出的每篇新文章,按「公众号名 + 标题 + 原文链接」拼成一条消息,循环调用上面的接口发出去,群里就会实时出现一条条带来源、带链接的更新提醒,点开链接就是原文,不需要再回到微信里确认。

如果希望消息里直接带正文摘要而不只是标题和链接,文章列表接口返回的字段里就包含 Markdown 正文(`contentMarkdown`),可以截取前几百字拼进消息卡片里,减少群成员点开原文确认内容的次数。

### 第五步:用 CLI 快速验证脚本逻辑

正式接入自动化流程之前,可以先用 [CLI 工具](/cli/) 在本地手动跑一遍同样的查询逻辑,确认哪些号真的有新文章、字段取值是否符合预期,再把验证过的逻辑搬进定时任务脚本,减少上线后出错的概率。

### 第六步:把 X 账号的更新并入同一套推送逻辑

如果团队同时需要监测一些 X(Twitter)账号,Mp2RSS 同时支持订阅 X 账号,推文与长文同样以结构化数据交付,调用方式和公众号文章接口类似,可以用同一套定时脚本逻辑,把两类信息源的更新统一推进同一个群,不需要为不同平台分别维护两套机器人脚本。

## 群机器人推送与人工值守监测的对比

| 维度 | 人工值守刷公众号 | 群机器人自动推送 |
| ---- | ---- | ---- |
| 依赖程度 | 依赖特定负责人是否在线、是否记得看 | 定时脚本自动运行,不依赖个人状态 |
| 信息同步 | 停留在负责人的微信里,需手动转发 | 自动出现在团队协作群,全员同步可见 |
| 交接成本 | 监测重点存在个人经验里,难以完整交接 | 订阅列表和脚本逻辑可直接复用,交接即切换账号 |
| 可追溯性 | 群内零散转发,难以系统检索 | 结构化数据留存,随时可用 Open API 重新查询 |
| 更新到账时间 | 不透明,受刷号频率影响 | 平均 2–3 小时数据可见,叠加脚本轮询间隔 |

## 常见问题

**需要自己搭建服务器才能跑这个推送脚本吗?**
不一定。定时拉取 + 推送群机器人的逻辑很轻,用低成本的云函数(按次计费,几乎不产生费用)或者一台已有的小型服务器跑定时任务都可以,核心只是按固定间隔调一次 [Open API](/api/),再调一次企业微信/飞书的 Webhook 接口。

**公众号刚订阅就能收到以前发过的文章提醒吗?**
不能。首次订阅只从订阅时刻起收录新文章,不会回溯历史,所以计划长期监测的号,建议尽早订阅,避免真正需要数据时才发现没有历史积累。

**一个团队账号能管理多少个公众号的监测?**
取决于购买的套餐档位,49 元/月 50 个订阅、99 元/月 100 个、399 元/月 400 个,功能完全一致仅上限不同,详见[会员与计费](/guide/membership)。

**除了企业微信和飞书,这套方法能用在 Slack 之类的工具上吗?**
可以。思路是通用的——只要协作工具提供「自定义机器人 + Webhook 地址」这类能力,都可以用同一套「Open API 拉增量 → 拼消息 → 调 Webhook」的脚本逻辑接入,只是消息体的字段格式要换成对应工具要求的格式。

**群机器人推送和订阅 RSS/邮件简报相比,应该怎么选?**
看信息的消费场景:如果团队日常协作本来就在企业微信/飞书群里完成,群机器人推送能让更新直接出现在大家已经在看的地方;如果更习惯用 RSS 阅读器或邮箱处理信息,直接订阅 [Mp2RSS 生成的标准 Feed](/guide/quick-start) 会更省事,两种方式用的是同一份底层数据,也可以同时使用、互不冲突。
